# 用 AI 写软件时,控制从哪里来

讨论备忘,2026-09-03。起因是一句诊断:**传统软件工程那套方法,用了 AI 之后好像全消失了,
完全不可控。**这篇是那次讨论的结论、已经落地的部分、以及**已知的漏洞**。

不是规范,是一份工作文档。里面的判断可以被推翻 —— 但推翻它的应该是事故,不是偏好。

## 1. 消失的到底是什么

方法没有消失。**消失的是其中依赖"人逐行敲代码"的那一半。**

以前的可控性有很大一部分是**免费**的:你写不出 500 行自己不理解的代码。那份理解是
打字这个动作附赠的。现在生成速度变了,附赠没了,理解必须**单独花钱买**。

而剩下那一半 —— 测试、类型、CI、小步提交、门禁 —— 不但没消失,价值还涨了,
因为它们是**机器执行**的,不依赖模型的配合。

所以方向不是"重建靠读完所有东西来理解"(那条路和生成速度赛跑必输),而是:

> **找到那些"人的一次廉价阅读,能约束住机器的一次昂贵写入"的点。**

推论,也是这篇里最强的一条主张:

> **把约束从 prompt 挪到 guard。**
> 每写下一条约束,就问"它能不能变成一个检查?"
> - "不要重构 index.html 的结构" → 一条断言结构不变量的测试
> - "部署前必须跑完整测试套件" → 部署脚本在套件没通过时**拒绝执行**
>
> 每一条完成毕业的规则,就不再依赖模型的品行。任务备忘框是约束的**暂存区**,不是终点;
> 一条规则待在框里,说明它还软。

## 2. 一场真实会话里的证据

这些判断不是推演,来自 2026-09-03 那一天的实际过程。

**人抓到的问题,没有一个是靠读 diff 抓到的**:tab_name 取错、`ccsid` 没生效(跑的是
另一份拷贝)、按钮文案不对、切走再回来还显示"keep 5m"、复制按钮会顺带进入 session。
全是在**看运行中的东西**,好几次是截图。

**模型自己最糟的几次失败,同样在 diff 里看不见**:

| 事故 | 为什么 diff 看不见 |
|---|---|
| 把一个函数插到了 HTML 文件最开头(HTML 头之前) | `node --check` 照样通过 —— 那段确实是合法 JS |
| 手拷文件进部署目录,绕过部署脚本的变更检测 | 文件是对的,**进程跑的是 6 小时前的旧代码** |
| 单实例守卫按进程名匹配,匹到了另一个 agent 的实例 | 逻辑"看起来对",直到它把 8443 弄停 |

由此:

> **验证必须打在"跑着的系统"上,不是"文件"上。"文件对了" ≠ "进程在跑这份文件"。**
> 模型改文件的速度远快于它确认部署的速度,这个落差就是 bug 的住所。

还有一条当天反复做、最值得固化的:

> **写完断言,去把代码改坏,确认它真的会 FAIL。**
> AI 写的测试的典型失效不是"测错了",是"空转也通过"(这个项目里出现过
> `check(..., True)` 这种什么都没断言的东西)。**没见它失败过的测试不算证据。**

以及关于注释的一条,不是文风问题:

> AI 代码里代码本身是廉价、可重新生成的,**稀缺的是理由**。
> 下一个 agent(或者一周后毫无记忆的同一个)不知道理由,就会把同一个 bug 重新引一遍。
> 所以注释写"为什么",并且带上测出来的数字和它防住的那次事故。

## 3. 已经落地的部分

**任务备忘(per-session)** —— `⚙ → 任务备忘`,全屏,两个框:

- **当前任务**:随进展改写。
- **注意事项**:与当前任务无关、这个 session 长期有效的规矩。

两个框分开的理由:**它们过期的速度不同**。合成一个,每次改任务都要把长期那半段重敲一遍,
那就是它开始失效的方式。

实现要点(细节见 `cc_web.py` 的 `/api/session-memo` 与 `static/index.html` 的 `memo*`):

- **一个 session 一个文件**(`~/.claude/cc_web_memo.d/<sid>.json`,按 agent 分域):
  两个实例同时写不会互相盖,忘掉一个 session 就是删一个文件。
- 轮询只带这个文件的 **mtime**(`memo_ver`,约 20 字节),文字只在它变了才取 ——
  跨设备能同步,又不必每次轮询搬同样的字符串。
- 按钮**只把文本填进输入框**(带 `[当前任务]` / `[注意事项]` 标记),不直接发送。
  一键直发是"一次误触换一次不必要的打断";而你伸手去按它的那个理由,通常还需要补一句话,
  那句话只能写在能编辑的地方。
- 因此"已发送 N 次"记在**真的发出去**的时候(composer 认开头的标记),
  手打一条同样计数。
- 记录里预留 `supervisor` 字段(恒为 null,接口拒绝写入),留给将来的监督者。
  留它的理由不只是省一次迁移:**这里存的是人写的版本**;模型自己总结的当前任务,
  恰好在它跑偏时最不可信。

**可以复用的现成设施**:`ask-peer` 两个方向都通(实测 claude→codex 9.1s,
codex→claude 254s);部署脚本会做变更检测 + 健康检查;测试套件自动发现
`tests/test_*.py`;实时预览已有"过期就不装作新鲜"的判定(离开时刻 vs 内容变化时刻)。

## 4. 四层结构

多一层只有在**错误不相关**时才增加可靠性,否则只是多一份让人不想看的报告。
相关性来自三处:同一个模型、同一份上下文、同一套取证方式。

职责**不重叠** —— 三层结构最典型的病是责任扩散,每层都指望别层会抓到:

| 层 | 它回答的问题 | 谁来做 |
|---|---|---|
| **0 事实** | **发生了吗?** | 脚本 / 测试 / 门禁(**无模型参与**) |
| **1 自检** | 哪条没满足,为什么 | session 自己 |
| **2 他检** | 做的是不是要求的 | 另一个 session(**唯一的判断层**) |
| **3 驱动/看门狗** | 有没有人在管 | 自己做的小东西 |

**层 0 是承重墙。**`git status`、测试结果、部署门禁的戳、结构不变量断言、
"进程跑的是不是我改的那份文件"。它们的错误和所有 LLM 层都不相关(没有模型参与)。
上面每一层都应该**消费**层 0 的产出,而不是各自去采证。没有层 0,
上面三层就是"用散文评论散文"。

### 各层的设计约束

**通用两条:**

1. **只报偏离,全绿压成一行。** 一份 12 项全绿的报告,看两周就不看了 ——
   而它一定常绿,因为是我们自己写的。**要吵得少而准,不要天天报喜。**
2. **每个结论必须带可核验的证据行**(命令 + 原始输出片段)。这样错的结论不用重做工作
   就能看出来;更重要的是**层与层意见不一致时是可诊断的**,而不是只让人更困惑。

**层 1(自检)**:擅长机械型约束("测试跑了吗"、"动过 index.html 吗"、"有没有未提交的改动"),
因为这些不靠内省,靠去看世界。对判断型约束("有没有偏离任务")基本没用 ——
让产出工作的同一个模型、在同一份上下文里给自己打分,而跑偏的典型形态恰恰是它自认为没偏。
**检查项应该首次推导后固定下来**(写回记录),之后每次只对同一张清单求值:跨次可比,
能看出它开始漏项。每次现拟的清单,会在拟题这一步就开始漂。
**skill 里要明写:只报告,不动手。**

**层 2(他检)**:一条具体的、最要紧的规则 ——

> **不要把 transcript 喂给它。**
> 只给两样:**备忘**(意图,人写的)+ **产物**(diff、测试输出、git 状态、跑着的系统、
> 层 0 的报告)。给了 transcript,就把被检者的框架和它一路给自己找的理由一起重新导入,
> 独立性当场蒸发。它要做的是"拿现实对意图",不是"拿它的说法对它的说法"。

真正的独立性来自**没经历过这个 session**,而不是来自模型不同 —— 一个全新的同种 session
同样具备。所以"用 codex 查 claude"**是口味变化,不是主要来源**;为一点边际独立性
付 25 倍延迟(9.1s vs 254s)不值。

**层 3(驱动/看门狗)**:它的独有能力不是判断力,是**在没人叫它的时候仍然在看**。
停住的 session 没法发现自己停住了;层 1 需要它配合去跑,层 2 需要有人去叫,
只有一个外部时钟能注意到"什么都没发生"。它也是**唯一在 session 卡死时还能工作的层**。

但 **"别停"本身不是好事**。从外面看两种停完全一样,价值相反:

- 停在"有明确剩余工作"上 → 驱动是纯赚;
- **它就该停** → 驱动有害。等人决策、被外部事实卡住,以及最危险的:它不知道下一步干什么。
  给一个无事可做的 LLM 一句"继续",它不会闲着 —— **它会编出工作来**。
  在这个仓库里那是最坏的结果。

所以:

> **驱动器不是"继续"按钮,是"接着做这件指名的事"。**
> 下一步必须由模型之外的东西命名(备忘里的任务、层 0 的事实、上一轮声明的未完项)。
> **指不出名字就不要推,升级给人。**

其余护栏:

- **有界 + 退避 + 看进展**:推一次之后既没有新 commit 也没有新 tool call,就别再推 ——
  那不是推进,是烧 token。
- **推动 ≠ 授权**。若一个 session 正等"要不要部署到四台机器?",而看门狗发来"继续",
  它很可能读成"是"。标记里必须写明:**这是机器唤醒,不构成对任何需要人确认的动作的许可。**
- **驱动 ≠ 替人按确认**。遇到权限弹窗只能**报告**"这个 session 卡了 40 分钟",不能去点。
  "自定义 judge"是另一件事、危险等级完全不同,要单独显式武装,不能顺着这个功能悄悄长出来。
- **看门狗自己不碰活儿**:只发唤醒,不改文件、不部署。
- **在场感知**:你在这个 session 里刚打过字 → 绝对沉默(你在亲自驾驶,机器插话只会撞车);
  你在任何 session 里活跃 → 把阈值调长(你随时可能走过来)。
  **真正的生态位是"人不在场的时间"** —— 你在的时候,你的下一条消息就是最好的驱动器。
- **最长生效时间**,而且要两个出口:**到期** + **任务完成信号**(层 0 的事实)。
  只靠钟不够,你担心的"任务早完成了它还在跑"在窗口内就会发生。
- **到期要留痕**,不能静静消失:写下"为什么停、当时什么状态"。
- **安静但可见**:开着没事做 和 关着,在界面上必须长得不一样(gear 里显示剩余时间 + 续命)。
  **按 session 开**,不是全局。
- **追加式日志**(不可让):它在人不看的时候动手,所以每次唤醒都要记 —— 时间、
  依据哪条事实、发了什么、之后有没有产生新的 commit / tool call。人回来第一眼看这个,
  而不是去读四个 session 的 transcript 猜。

**它也顺便解决了"他检谁来叫"**:让被告自己请裁判不合理,由看门狗按确定性条件叫
(任务改过、有 N 个新 commit、但没做过他检)。

## 5. 已知漏洞(按严重程度)

1. **整套机制没有"完成"的定义。** 每层都在问"任务满足了吗",可任务是散文;
   散文只能被解读,不能被检查 —— 这是层 1/2 退化成作文的根源。缺的不是层,是**验收条件**:
   写任务时顺手写下 1–3 条"怎样算做完"。有了它层 0 能直接执行一部分,层 1 只需取证,
   层 2 只判断残差,看门狗终于有**真的完成信号**而不是靠 commit 猜。
   传统 SE 里消失得最彻底的其实就是这个。**一个字段的成本,收益最高。**
2. **没有任何一层会问"要求本身是不是错了"。** 目标过期得很快;
   **一份对着过期任务全绿的自检比没有更糟**,它给错的东西盖了章。
   需要一条便宜的反向通道:发现与任务冲突的事实时,能把备忘标成"有异议 + 一句理由",
   而不是在某一轮散文里提一句然后随对话消失。
3. **"只报偏离"没有定义,所以会自己塌掉。** 偏离由模型判定的话,
   它会在最需要报警的那天把偏离定义得很窄。必须对着**验收条件和注意事项**逐条判定。
4. **四层共享证据,所以共享盲区。** 层 0 没测的东西,上面永远发现不了。
   唯一的解法是流程规矩:**每次真实事故必须毕业成一条层 0 检查,否则一定复发。**
   现成候选三条(都来自 2026-09-03,当天全靠人肉发现):部署树漂移、
   "文件对了但进程跑的是旧的"、按进程名匹配的单实例守卫。
5. **层 2 不便宜。** 要读 diff + 产物,是实打实一轮:分钟级、烧 token、需要一个活的 session。
   得有配额,以及"改动小于某规模不值得叫他检"的门槛。
6. **一切都是 per-session,可工作不是 per-session。** 一件事横跨多个文件 + 多台主机。
   活体标本:某台机器睡着导致的欠账(配置项 + iTerm 设置 + 两批部署)记在这个 session 里,
   而没有任何东西会去捡它。**需要一份不属于任何 session 的未完项清单(跨会话/跨主机)。**
7. **武装看门狗这件事,人仍然是单点。** 忘了开 → 什么都不发生;忘了它开着 → 它一直跑。
   到期/在跑必须**在人本来就会看的地方自己吱声**(tab title、brief 行),
   不能藏在要点开才看得见的 modal 里。
8. **跨 session 没有记忆。** 注意事项是 per-session 的,每开一个新 session 就重新失忆。
   `CLAUDE.md` 是全局的且会过期。中间缺一层:**项目级注意事项,新 session 继承,
   允许 per-session 覆盖。** 否则那个框永远靠复制粘贴维护 —— 而复制粘贴就是它失效的方式。
9. **在造一个没有反馈的控制系统。** 至少记三个数:层 0 抓到的事故数 vs 人事后发现的;
   有多少条注意事项**毕业**成了门禁;每次唤醒之后是产生了进展还是纯烧 token。
   不记这些,一个月后会有四层机制、却不知道哪层在挣钱。
   **先验:层 0 大概挣走绝大部分,层 2/3 挣一点。**
10. **最终失败形态是"变成仪式"。** 维护这套控制系统比它省下的注意力更贵,
    于是开始盖橡皮章。解药只有一条硬规矩:**任何一样东西 N 周内没抓到过真问题就删掉** ——
    包括已经写好的。

**一条不是漏洞、而是设计约束的判断:**

> **模型不是它自己治理的可靠参与者。**
> 凡是依赖它自报的环节(未完项、"我卡在人身上了"、偏离判定),它都能不知不觉地弱化 ——
> 不是使坏,是因为它在优化"看起来做完了"。不依赖它配合的只有两样:
> **层 0 的事实,和看门狗的钟。**整套机制的重量应该压在这两样上;
> 自报只能当作**给看门狗的线索**,永远不能当作完成信号。

## 6. 建设顺序

1. **部署门禁**(层 0 第一块砖,约 20 行):当前工作树的 git hash 没有对应的套件通过记录 →
   拒绝部署。它产出的"戳"正是看门狗判断"任务是否完成"的事实来源。
   (当天已经手工绕过部署脚本一次 —— 这条规则目前完全靠自觉。)
2. **验收条件字段** + **报告格式**定下来(`<sid>.check.json`:项、状态、证据行、
   针对哪版任务)。**格式是四层的集成点**:1 和 2 都往这个格式里写,3 读它。
   格式先定,后面三层才不会各写一套散文。
3. **服务端持久化"最后人类活动时刻"**。**已查证:现在没有** ——
   `keepAlive()` 只改客户端本地变量(`activityDeadline`),关掉页面就没了。
   看门狗的在场感知依赖这个,得先补。
4. **看门狗本体**:cron + 确定性规则,只做三件事之一 —— 拼出**指名的**驱动语句、
   叫一次他检、**升级给人**。三条路都不需要它自己有判断力。
5. **层 1 自检 skill**(最便宜,顺便把格式跑通)。
6. **层 2 他检**:走 `ask-peer`(两个方向已验通),守住"不给 transcript"。

**如果只能做三件:** 验收条件字段(漏洞 1)、部署门禁 + 事故毕业规矩(漏洞 4)、
不属于任何 session 的未完项清单(漏洞 6)。三件都不需要模型有判断力、
也都不依赖模型配合 —— 而它们恰好覆盖了当天真正出事的那几处。

## 7. 未决

- **检查项**首次推导后固定(推荐,可比、能发现漏项),还是每次现拟(灵活但不可比)?
- **项目级注意事项**放哪、怎么继承与覆盖?
- **跨 session 未完项清单**放哪(不能是 session 域的文件)、谁有权写?
- 看门狗的**在场阈值**具体多久(本 session / 全局两个尺度各一个数)?
- 验收条件里**可机械执行的部分**用什么写(shell 片段?测试名?)——
  能执行才能进层 0,不能执行的只能留给层 1/2。
