# self-check — 对着任务和注意事项,核对现实

cc-web 的 `⚙ → Task` 里,人写了两样东西给这个 session:**当前任务**(随进展改写)和
**注意事项**(与任务无关、长期有效的规矩)。这个 skill 的工作是**拿现实去对它们**,
产出一份带证据的报告。

## 三条硬规矩(比怎么做更重要)

1. **只报告,不动手。** 发现某项没做完 —— 哪怕修它只要一行 —— 也**不要**修。
   人要的是"我现在处于什么状态",一边查一边改会把这个问题本身弄没。
   同理:**不要去执行任务本身**。任务说"做 X"而 X 没做,你报告 `not_done`,不是去做 X。

2. **任务不是给这个 session 的,就直说,不将错就错。**
   备忘可能写错了地方 —— 写给另一个项目、另一台机器、另一个 session,或者是 resume 之后
   串了。这种情况**必须**给出 `verdict: "not_mine"` + 理由 + 证据(这个 session 的 cwd、
   所在仓库、实际动过的文件),然后**停下**。
   绝对不要"看起来沾点关系就当成自己的任务去执行"。

3. **证据来自世界,不来自记忆。** 每一条结论要附上你**真的跑过**的命令和它的**原始输出**
   片段。"我记得我跑过测试"不是证据 —— 去看戳、看 git 状态、看文件、跑一次。
   脚本会**拒收**没有证据的结论(这是故意的:让产出工作的同一个模型给自己打分,
   本来就最不可靠,所以结论必须是可以十秒核实的)。

## 步骤

```bash
SC=~/.claude/skills/self-check/selfcheck.py
python3 "$SC" facts          # 要检查什么 + 确定性事实(JSON)
```

配置只有一份:`~/.claude/cc_web.conf`(取 `token=`)。报告存哪、这是哪个 agent,
都**问 cc-web**,不在这里重新推导 —— 否则 cc-web 改了目录名,这个 skill 会静默读到空。
因此它需要本机的 cc-web 在跑(那份任务备忘本来就住在里面)。

`facts` 给你:`task` / `notes` 原文、`memo_ver`(任务版本)、`pinned`(已固定的检查项清单,
可能为 null)、以及 git 状态(分支、HEAD、脏文件、未 push、最近提交)。

1. **先判归属。** 任务描述的是这个 session 在做的事吗?对不上就走 `not_mine`(见规矩 2)。
   没有任务也没有注意事项 → `verdict: "no_task"`,一句话结束。

2. **检查项清单。**
   - `pinned` 非空 → **原样复用那几条 claim**,一个字都不要改。
     (脚本会校验:任务没变而清单变了 → 拒收。理由:每次现拟清单的模型,
     会在拟题这一步就开始漂 —— 悄悄不再检查那条最难受的。)
   - `pinned` 为 null(首次,或任务改过) → 从 task + notes 里推导 **1–5 条**可检查的陈述。
     每条要能被一条命令或一次查看**证伪**。宁少勿多,**不要为了显得周全而凑数**。
     推不出可检查形式的,如实写成 `unverifiable` 并说明"怎样才能变得可检查"。

3. **逐条求值,靠去看世界。** 常用的:`git status --porcelain`、`git log --oneline`、
   `git diff --stat`、跑测试套件、`ls -l` 看时间戳、`grep` 看某个约束是否被破坏、
   `curl` 看部署后的实际行为。**注意事项也要查**(它们是"有没有违反",不是"有没有完成")。

4. **写报告并保存:**

```bash
cat > /tmp/selfcheck.json <<'JSON'
{
  "verdict": "deviations",
  "summary": "一句话",
  "items": [
    {"claim": "测试套件在当前工作树上通过",
     "status": "not_done",
     "evidence": [{"cmd": "bash tests/run_all.sh", "out": "FAILED (1): ..."}],
     "note": "可选"}
  ],
  "disputes": [{"about": "task", "reason": "任务假设了 X,但实测 X 不成立"}]
}
JSON
python3 "$SC" save --file /tmp/selfcheck.json
```

脚本把报告**交给 cc-web 的门禁**(`POST /api/session-check`),不是自己写文件 ——
校验规则住在服务端:住在这个脚本里的话,agent 直接写 JSON 文件就绕过去了。

`verdict` 取值:`ok`(全部符合)、`deviations`(有未满足/部分满足)、`not_mine`、
`disputed`(任务/注意事项本身有问题)、`no_task`。
`status` 取值:`done` / `not_done` / `partial` / `unverifiable`。

脚本会拒收这些(都是故意的):没有证据的结论;任务未变而清单被改;有未完成项却报 `ok`;
`not_mine` 没给理由和证据。`memo_ver`、`checked_at`、`git` 由脚本自己盖,你不要填 ——
报告不能声称自己针对的是另一个版本的任务。

## 报告放哪 / 怎么看

由 cc-web 存,一个 session 一个文件(它自己决定路径,按 agent 分域)。三种看法:

- `python3 "$SC" show` —— 终端里看上一份;任务在那之后被改过时会先警告"针对更早版本"。
- **cc-web:`⚙ → Task` 那一行的第二个按钮「自检」** —— 按钮上直接显示 `✓` / `✗2` / `⚠`,
  点开就是逐项 + 证据。
- `GET /api/session-check?claude_session_id=<sid>` —— 给将来的看门狗/他检用。

**它故意不写进人的备忘文件** —— 那份是人拥有的,agent 的读-改-写不该有机会盖掉人写的话。

## 两件值得多说一句的事

**任务本身可能是错的。** 你在干活途中发现的事实与任务冲突时,用 `disputes` 说出来
(必要时 `verdict: "disputed"`)。一份对着过期或错误任务全绿的自检,比没有自检更糟 ——
它给错的东西盖了章。不要"绕过去然后照做"。

**全绿就一行。** 都符合时 `summary` 写一句话即可,不要展开成十二行报喜 ——
天天报喜的报告,两周后没人看,而它一定常绿(因为是你自己写的)。偏离才值得占篇幅。

## 自检治不了什么(别装作能)

同一个模型、同一份上下文给自己打分,对**机械型**约束很有用("测试跑了吗"、"动过那个文件吗"、
"有没有未提交的改动"),对**判断型**约束基本没用("有没有偏离任务"、"是不是最简做法")——
后者的正确做法是让另一个没经历过这个 session 的人/agent 来看。所以:
**能变成命令的就去跑命令,不能的就老实标 `unverifiable`,不要用自信的散文补位。**
